# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A 500-challenge CSS curriculum. Every challenge is a GitHub issue; solutions land as a branch, a PR reviewed against `docs/REVIEW-CHECKLIST.md`, and a squash merge. The repo exists to build employable CSS skill and to leave a public record of it, so the workflow matters as much as the code.

Repo root holds `curriculum/`, `docs/` and `scripts/`; `frontend/` is the only package. Run pnpm commands from `frontend/`.

### Curriculum data flow

`curriculum/challenges.json` is the single source of truth for all 500 challenges (id, slug, title, phase, difficulty, acceptance criteria, rendered issue body). Two things derive from it, both regenerated by `pnpm sync:curriculum` and never hand-edited:

- `frontend/src/challenges/curriculum.generated.ts` — drives the app's sidebar and progress bar.
- `docs/CURRICULUM.md` — the readable index.

`curriculum/issue-map.json` maps challenge id to GitHub issue number and is written by `scripts/seed-issues.mjs`; the sync script merges it in so the app can deep-link to tickets.

### Challenge folders

`scripts/new-challenge.mjs` (`pnpm new <id>`) scaffolds `frontend/src/challenges/<NNN>-<slug>/` with `index.tsx` + `styles.css`. There is no registration step — `registry.ts` discovers folders with `import.meta.glob` and lazy-loads them, and `builtIds` is what the sidebar uses to mark a challenge done. `000-example` is the shape reference, not a ticket.

Class names inside a challenge are prefixed `c<NNN>` because all challenge CSS is global and unscoped. Challenge stylesheets must not use the `--ui-*` custom properties — those belong to the app chrome in `index.css`, and the point of the exercise is to build your own tokens.

Package manager is **pnpm** (`pnpm-lock.yaml`, lockfile v9). React 19, Vite 8, TypeScript 6, ESLint 10 flat config. There is no test runner configured.

## Commands

All run from `frontend/`:

```bash
pnpm dev              # Vite dev server, challenge browser with HMR
pnpm build            # tsc -b (project references) then vite build -> dist/
pnpm lint             # eslint .
pnpm preview          # serve the production build from dist/
pnpm new <id>         # scaffold a challenge folder
pnpm sync:curriculum  # regenerate curriculum.generated.ts + docs/CURRICULUM.md
```

From the repo root:

```bash
node scripts/seed-issues.mjs      # create any missing challenge issues (resumable, rate-limit aware)
SEED_LIMIT=5 node scripts/seed-issues.mjs
```

`pnpm dev` does **not** type-check — Vite strips types via esbuild. Only `pnpm build` (the `tsc -b` step) surfaces type errors, so run it before declaring TS work done.

## Styling architecture (app chrome)

No CSS framework, no CSS Modules, no preprocessor. Two global stylesheets, split by role:

- `src/index.css` — imported by `src/main.tsx`. Owns the design tokens (custom properties on `:root`: `--text`, `--bg`, `--border`, `--accent`, `--shadow`, plus `--sans`/`--heading`/`--mono`), the dark-theme override block, base element styles (`h1`, `h2`, `p`, `code`), and the `#root` app shell — a flex column capped at `1126px` with `border-inline`, which is what produces the framed page look.
- `src/App.css` — imported by `src/App.tsx`. Styles for the shell only: `.shell`, `.sidebar`, `.stage`, `.dashboard`.

Conventions this codebase already commits to — follow them rather than introducing a parallel approach:

- **Native CSS nesting** everywhere, including nested `@media` blocks inside a selector. No build-time nesting plugin; this relies on browser support.
- **Theming is token-swapping only.** `@media (prefers-color-scheme: dark)` redefines the `:root` custom properties; individual rules never branch on theme. New colors belong in the token block, not inline in a rule.
- **One breakpoint: `max-width: 1024px`.** Repeated in both files as nested media queries. Adding a second breakpoint means touching every section, so prefer reusing this one.
- Class names are **global** — there is no scoping mechanism. Section-level styling is done by `id`.

## Assets

Two different mechanisms, and mixing them up breaks the build or the URL:

- `src/assets/*` (`react.svg`, `vite.svg`, `hero.png`) are **imported** into TSX and get hashed/rewritten by Vite.
- `public/icons.svg` is an **SVG sprite** referenced by root-absolute URL, never imported: `<svg><use href="/icons.svg#github-icon" /></svg>`. Available symbol ids: `documentation-icon`, `social-icon`, `github-icon`, `discord-icon`, `x-icon`, `bluesky-icon`. Adding an icon means adding a `<symbol id="...">` to that file. `public/favicon.svg` is likewise served as-is from `/`.

## TypeScript setup

`tsconfig.json` is a solution file with project references only:

- `tsconfig.app.json` covers `src` (DOM libs, `jsx: react-jsx`, `types: ["vite/client"]`).
- `tsconfig.node.json` covers `vite.config.ts` only (Node types, `module: nodenext`).

Both enable `noUnusedLocals`, `noUnusedParameters`, `erasableSyntaxOnly`, and `verbatimModuleSyntax` — so an unused import fails the build, and type-only imports must be written `import type { X } from '...'`.

## ESLint

Flat config (`eslint.config.js`) extending `js.configs.recommended`, `tseslint.configs.recommended`, `reactHooks.configs.flat.recommended`, and `reactRefresh.configs.vite`. Rules are **not** type-aware (no `parserOptions.project`). The react-refresh rule means a module exporting a component should not also export non-component values, or HMR degrades to a full reload.
